# Innocence AI 智能助手与自动化系统方案评审

## 1. 本轮需求与评审结论

用户希望新增一个 AI 自动化模块，通过自然语言指令提供建议、一键规划任务计划和当前安排。本轮提供三个产品方案，区别在于助手能执行到哪一步，以及是否在用户离开后继续运行。

用户已于2026-10-04明确“采用b方案”。模块名称为「智能助手」，采用B：既能给建议，也能把指令变成可预览、可编辑、可应用的真实任务安排。C的定时与事件规则仍是后续候选，未包含在本次选择中。

本文件保留三方案比较。B的正式范围、阶段与首批开发契约见`Innocence-AI智能助手B方案实施与契约.md`，对应DEC-0050/0090。原有15个模块的封板记录保留，新增第16模块智能助手范围确认、实现待完成；供应商、费用和发行版本另定，原验收门禁不自动通过。文中示例均为合成场景。

## 2. 现有能力与必须承接的边界

| 已核对的基线 | 对新模块的影响 |
|---|---|
| Flutter Windows + Android，Spring Boot 后端 | 共用助手业务模型，分别设计桌面与手机布局 |
| 日计划最小单位为半小时 | AI 写入必须遵守 30 分钟网格；不能把用户明确要求的 45 分钟静默改成 60 分钟 |
| 月计划为完整月历，含可复用任务存档及批量套用 | 月度安排落到具体日期；“未来七天”只是日期范围，不新增周计划权威层级 |
| 年度任务按月份跨度管理，与日/月计划独立 | 可分别提出年度目标、月度安排、每日任务，逐类选择创建；默认不建立自动进度联动 |
| 年度进度 0–100%，子任务状态独立 | 助手不能根据聊天或专注时长猜测任务已完成，首版不自动修改年度进度 |
| 已过期未完成计划不自动转入次日 | B 可按用户指令提出重排；C 的自动顺延属于新业务规则，需另行决策后才可实施 |
| 在线账号和本机离线 ownerScope 隔离 | 生成、预览、执行、历史与偏好均绑定当前身份；切换账号后旧提案不可直接执行 |
| 签到需用户手动点击并满足既定条件 | 助手可提示条件，不能代签或伪造学习与完成记录 |
| Android v1.2.2 正式包无 INTERNET 权限 | 云端 AI 需要另一个明确的联网实施阶段；当前离线包不能声称能连接模型 |
| Windows Large/Medium/Small + 主动 Focus Orb；Android 三点侧栏 | 助手承接现有导航与主题，不把完整聊天页面缩进专注球 |
| 真实同步、实体手机和 Windows 完整矩阵仍待验收 | AI 上线不能代替这些原有门禁；需新增自身证据 |

事实依据：`docs/08-project-profile.md`、`docs/06-contract-inventory.md` U14–U23、`docs/07-dataflow-and-module-map.md`、项目计划书学习计划关键规则，以及进度 0053/0088。

## 3. 三套方案对比

| 比较项 | A：规划顾问 | B：指令式执行助手（推荐） | C：持续日程管家 |
|---|---|---|---|
| 核心定位 | 帮用户想清楚怎么安排 | 用户说一句话，生成并应用安排 | 用户设定目标和规则，持续协助调整 |
| 自然语言沟通 | 支持 | 支持 | 支持 |
| 当前安排与容量分析 | 只读 | 只读并支持提出修改 | 定时或事件触发分析 |
| 保守/均衡/紧凑候选计划 | 支持 | 支持，可按候选方案应用 | 初始支持，后续按规则更新草稿 |
| 写入日/月/年计划 | 用户在原页面手动创建 | 应用选定提案；明确指令可直接执行符合授权的新增 | 仅在用户预设范围内执行白名单动作 |
| 时间冲突处理 | 指出并解释 | 硬性校验、给出差异、再写入 | 规则触发后重新校验，并避免改动锁定任务 |
| 长期后台运行 | 无 | 无 | 有，需要持久化规则与调度器 |
| 执行历史和撤销 | 保存建议历史即可 | 必需 | 必需，另有规则运行历史 |
| 相对开发量 | 较低 | 中等 | 较高 |
| 模型调用成本 | 用户主动请求时发生 | 主动请求、局部重生成时发生 | 另有定时及事件调用，需要配额 |
| 适合的目标 | 先验证规划建议是否有用 | 实现“一句话帮我安排”的核心体验 | 产品成熟后提供长期协助 |

开发量与成本是相对比较，不是工期或费用承诺。供应商、用户量、上下文长度和触发频率确定后再估算。

## 4. 方案 A：规划顾问

### 4.1 用户体验

示例指令：“我下个月要准备英语考试，工作日晚上两小时，周末半天，帮我做三套计划。”

助手先识别目标、期限和可用时间；只在缺失信息会影响安排时提问。读取用户允许的当前计划摘要，给出三种强度、每天或每阶段任务、预计占用与安排理由。用户可继续说“降低强度”“优先阅读”“周末不安排”。

结果为可查看的建议卡片。用户点击“打开计划页”，由自己在原计划页保存；A 不负责业务写入。“收藏建议”只保存助手建议，不等于已创建学习计划。

### 4.2 首版范围

- 目标拆解、任务排序、日程解释、当天剩余时间建议。
- 根据用户选定的时间范围，生成保守、均衡、紧凑三套候选方案。
- 显示已知安排、冲突、假设、缺失信息和可用容量；数据不足时不编造状态。
- 简单复盘：根据实际完成与专注摘要提出下一次建议，不推断用户情绪或给能力贴标签。

### 4.3 取舍

适合快速验证规划质量，写入风险低。用户仍需重复填写计划，离“一键安排”的目标有一段距离。如果选 A，建议把它当验证阶段，并保留升级到 B 的提案结构。

## 5. 方案 B：指令式计划执行助手

### 5.1 核心流程

1. 输入指令，例如“把未来 14 天工作日 19:00–21:00 的空闲时间安排成英语学习，已有计划保留”。
2. 读取当前身份下相关日期的安排和用户选择的偏好，标出数据时间与已知范围。
3. 生成候选计划，由确定性规则检查半小时网格、日期、容量、冲突、权限及字段。
4. 展示计划卡片和变更清单：新增几项、移动几项、影响哪些日期、保留哪些原任务。
5. 用户编辑或选定方案，点击“应用”；执行成功后显示实际保存结果与撤销入口。

默认“帮我规划”进入预览。用户明确说“直接新增到计划，不修改现有任务”，且日期、对象与内容完整、没有冲突，可在该指令授权范围内直接执行，无须再问一次相同问题。覆盖、删除、跨日期批量移动等操作必须先呈现准确影响，并取得对应确认；一次确认覆盖同一提案，提案内容改变后授权需重新匹配。

### 5.2 建议支持的指令

| 类别 | 示例 | 产生的结果 |
|---|---|---|
| 目标规划 | “一个月完成这本书，每天最多一小时” | 候选阶段任务与具体日期安排；没有章节信息时先补充或按明确假设出草稿 |
| 今日新增 | “明天晚上七点安排一小时数学” | 两个连续半小时格的任务，新增前检查当天占用 |
| 当前重排 | “今晚少了一小时，重新安排剩下的任务” | 保留已完成、正在进行与锁定任务，只提出未开始任务的差异 |
| 批量套用 | “把这份工作日安排用于本月剩余工作日” | 明确日期列表和每个日期的跳过/覆盖影响 |
| 任务拆解 | “把年度阅读目标拆成三个阶段，再安排这个月” | 分别预览年度任务/子任务与月历日期任务，不自动关联完成率 |
| 存档 | “把这套日程保存为考试复习模板” | 保存任务存档；同名更新必须提示影响 |
| 查询与复盘 | “今天先做什么”“最近七天哪里安排太满” | 基于实际数据的建议与摘要，列出数据缺口 |

不包含通用电脑控制、任意脚本、直接数据库操作、自动给队友发消息、自动签到或自动勾选完成。助手的首版动作围绕本人计划；社交与外部系统接入另开范围。

### 5.3 首版收敛顺序

先完成“日计划查询 → 多方案生成 → 无冲突新增 → 保存与撤销”。第二批增加日期批量安排、任务存档、未开始任务重排。第三批增加独立年度任务和多子任务生成。它们共同构成 B，首批完成不能声称整个 B 已交付。

首版使用文字输入。语音、附件识别和外部日历暂列扩展，避免把识别错误与排程写入同时引入。

### 5.4 取舍

最符合用户的直接指令与一键安排需求，可复用现有计划能力。主要工作是把模型建议转成可靠业务动作，并处理过期预览、保存失败、重复点击、双端冲突与撤销。聊天界面只是入口，执行结果必须以实际业务保存为准。

## 6. 方案 C：持续日程管家

### 6.1 用户体验

示例规则：“每天早上根据未完成目标生成今天的建议，晚上复盘；不要修改我锁定的任务，未经我同意不要覆盖已有安排。”

用户创建规则时能看到触发时间或事件、读取范围、可执行动作、最大调整范围、有效期、静默时间及通知条件。持续规则可随时暂停、修改、删除，提供“立即停止自动化”总开关。

### 6.2 自动化分级

| 级别 | 自动化能力 | 建议启用方式 |
|---|---|---|
| C1 | 定时生成今日建议/复盘草稿，用户选择应用 | 默认入口，最先实施 |
| C2 | 已授权目标、日期与空闲时段内新增本人未开始任务 | 用户主动开启，并设置数量、时间和有效期上限 |
| C3 | 按规则移动或顺延原任务 | 另行审阅业务规则；只操作明确授权集合，锁定/已完成/进行中任务除外 |

“规则执行”与“通知用户”分别设置。无变化或没有可执行内容时保持安静；完成、异常或需用户处理时才通知。规则失败不循环打扰，也不反复消耗模型额度。

### 6.3 必须解决的新问题

- 云端账号规则由服务端统一调度；两端只接收结果，避免手机和电脑重复执行同一规则。
- 用户长期离线时，云端只知道最后同步的安排；不得据此覆盖可能已变化的本地任务。提案同步回来后重新校验。
- 本机离线规则只能基于本机资料运行；电脑关机或手机进程不可运行时，展示错过执行，不补做过时写入。
- 每次规则运行均有唯一键，触发冷却、次数上限、费用上限和过期处理；先判断有无变化，再决定是否调用模型。
- 自动顺延过期任务与现行“过期未完成不自动转入下一天”存在差异。选择 C3 后必须新增决策，说明何时保留失败记录、如何避免反复迁移、原日期与新日期如何审计。

Android 的周期后台任务会受到系统优化和约束影响，不能承诺每天精确到某一分钟执行。因此建议把云端规则生成、设备接收、准点提醒作为三类能力分别设计和验收。依据：[Android 官方后台任务文档](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)。

### 6.4 取舍

长期价值较高，也最容易因过度调整、过多通知或双端重复触发损害体验。建议在 B 的实际保存、撤销、同步与数据质量稳定后再实施，先 C1，再按用户需求评审 C2/C3。

## 7. 同一场景下的三个方案

合成场景：用户希望未来 14 天工作日 19:00–21:00 学英语，其中一个日期 20:00–20:30 已有不可移动安排。

- A：指出该日期只有 90 分钟可用，给出降量、改用其他日期、调整目标的建议；用户自行保存。
- B：生成具体任务日期与时段，保留占用；显示“此日期缺少 30 分钟”。除非用户允许其他时间，否则不擅自放到 21:00 之后。用户选择降量或额外可用时段后再应用。
- C：首轮按 B 处理；之后按授权规则生成变化草稿或范围内新增。用户未授权顺延时，未完成任务不会自动搬到第二天。

另一个常见指令是“帮我合理安排”。助手需要先明确目标、截止日期、可用时间中真正缺失的条件，通常合并为 1–3 个问题。若用户只要建议，可以列明假设给草稿；实际写入不能依赖隐含假设。

## 8. 每次生成的三种计划强度

“A/B/C 产品方案”和“保守/均衡/紧凑候选日程”是两种选择。用户选择 B 后，仍可让助手一次产生不同强度的具体安排。

| 候选日程 | 建议策略 | 适用情形 |
|---|---|---|
| 保守 | 留较多可用容量，先覆盖高优先级目标 | 刚建立习惯、可用时间不稳定 |
| 均衡 | 在目标进度与缓冲之间取中间值 | 日常学习与工作，建议默认 |
| 紧凑 | 使用较多已授权空闲时间，明确展示容量压力 | 短期截止任务，用户主动选择 |

三种方案都遵守休息与睡眠等用户明确约束，不把紧凑方案作为评价用户努力程度的依据。如果指定期限与容量不相容，展示缺口，给延长期限、减小范围、增加可用时间三个方向，不保证不可实现的目标。

## 9. 双端页面提案

### 9.1 共用内容

助手页面提供四类内容：「对话」「计划提案」「执行记录」「自动化规则」。A 不显示执行与规则操作，B 提供前三项，C 增加规则管理。用户能随时看到当前账号/本机身份、模型或离线模式、读取范围，以及尚未保存的提案状态。

计划提案卡至少包含目标与日期、占用时长、冲突/容量、待补充项、假设、变更摘要和“编辑/应用/放弃”。保存后由执行记录给出实际结果，不能把模型的“已安排”文本当作成功。

### 9.2 Windows

- 首页增加“帮我安排今天”快捷入口；计划页增加“用 AI 规划/调整”，传递当前日期或用户选中范围。
- Large 使用左侧对话、主区提案、右侧安排差异；Medium 把详情放入抽屉；Small 使用单列对话与独立提案页。
- 初版建议放在工具入口，保持现有主导航；是否升级为主工作区随方案选择另行确认。
- Focus Orb 保持现行专注摘要和恢复页面行为；点击恢复后可进入助手，不加入完整聊天、自动接管或新常驻监控。
- 四主题共用同一业务内容与状态，分别承接既定视觉。

### 9.3 Android

- 从现有三点侧栏新增“智能助手”入口，计划页提供相关快捷入口；保留现行五个主入口。
- 输入区支持键盘与系统返回；提案进入全屏详情，批量修改使用清晰差异列表。
- 简约白色与液态玻璃共用 Material 3 表单和无障碍交互，单独核对窄屏、大字体、键盘遮挡与真机。
- 当前离线版展示“离线排程”，联网版准备完成后才出现云端模型选择与连接状态。

## 10. 模型接入与离线方案

模型部署是独立技术选择，不改变 A/B/C 的产品定位。

| 接入方式 | 建议位置 | 优点 | 代价与边界 |
|---|---|---|---|
| 服务端统一模型网关 | B 的在线首版优先方案 | 两端行为一致；密钥、配额和模型切换统一处理 | 有调用费用与网络依赖；需评审数据发送范围和供应商条款 |
| 用户自配模型接口 | 后续高级设置 | 用户自行选服务与承担额度 | 支持负担较高；需限制接口地址与访问范围，避免任意 URL 访问内网 |
| 本机模型 | Windows 后续可选 | 特定设备可减少向云端发送数据 | 安装、硬件、模型分发与性能需实际验证；不能承诺手机同等能力 |
| 本地规则排程器 | 双端离线基础 | 使用已选任务、模板、时段和优先级确定性排程 | 不具备开放式语言理解；应标明离线规则能力 |

建议首版云端生成仅开放给已登录在线账号，默认上下文为本次指令、相关日期的任务与占用摘要；不附加私信、团队聊天、全部备忘录或完整个人档案。用户选择附加内容时，显示具体范围与用途。供应商密钥只存在服务端安全配置，不打包到 APK、不进入 Git。

未登录本机离线资料只走本地规则。未来若支持将本机资料发给云端 AI，需单独设计明确的数据发送授权、请求身份与返回归属，不借用同步导入授权，也不伪造服务端账号。

联网 Android 是新增实施范围。实施时需明确 INTERNET 权限、真实认证、会话保护、失败恢复和用户数据发送选择；保持本机离线可用与发行签名连续，不直接把现行离线包标记为在线版。

供应商选择在方案确定后比较：中文指令/结构化输出表现、调用稳定性、时延、价格、数据处理条款和部署条件。本轮不绑定某个供应商或未经核验的价格。

## 11. 建议的执行架构与契约范围

建议链路：

```text
自然语言指令 + 已授权上下文
  → 模型适配器（理解目标/建议任务）
  → 统一提案模型
  → 规则排程与业务校验
  → 计划差异 + 授权检查
  → 业务执行适配器
  → 实际保存结果 + 执行记录 + 可撤销状态
```

模型负责理解和建议；确定性代码负责日期、时区、半小时网格、容量、冲突、权限、版本和幂等。模型不能获取 SQL、Shell、任意 HTTP 或直接修改数据库的工具。读取的备忘录或任务文本是内容，不能提升为执行授权。

将可执行动作限定为白名单并绑定当前用户，依据是项目租户规则；最小权限与对高影响动作设置确认也符合 [OWASP 关于 AI 过度代理能力的建议](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)。确认信号由程序验证，不能由模型自行声明用户已经同意。

### 11.1 复用与新增

- 现有参考：Flutter `SessionController`、`StudyPlanApi`、`OfflineStore`；服务端 `StudyPlanController`、`StudyPlanService` 与同步模块。
- 当前 `saveTodayPlan` 有在线 API 和离线 ownerScope 写入分支；新模块应复用其业务语义，不假定当前所有线上操作都已经先写本地。
- 建议新增 Flutter `assistant` feature 和服务端 `assistant` module，模型外部 DTO 经适配器映射到内部提案模型。
- 在线批量执行建议由服务端助手编排调用现有业务 service，在明确定义的事务单位内保存；客户端读取权威结果后刷新已有计划状态，避免再把同一提案重复写一次。
- 本机离线执行由本地适配器以同一 ownerScope 在本地事务中保存业务变更与 outbox；云端模型不参与离线写入。
- 单日执行建议原子提交。跨日或跨实体批量执行的全有全无/逐项结果必须先固化契约；现有批量套用不能直接当成新复合事务保证。

### 11.2 待评审的新接口方向

以下是契约设计输入，不是已存在接口。落实前需填写公共响应、错误码、认证、幂等、版本、超时与脱敏样本，并登记到接口清单。

| 建议接口 | 用途 |
|---|---|
| `POST /api/app/v1/assistant/proposals` | 根据指令生成提案，不产生业务写入 |
| `POST /api/app/v1/assistant/proposals/{id}/validate` | 对修改后的提案重新排程、校验并返回差异 |
| `POST /api/app/v1/assistant/proposals/{id}/execute` | 匹配当前身份、授权范围和数据版本后执行 |
| `GET /api/app/v1/assistant/executions/{id}` | 读取执行状态；处理请求超时但结果未知 |
| `POST /api/app/v1/assistant/executions/{id}/undo` | 版本一致时产生补偿变更，拒绝覆盖后续修改 |
| `POST/GET/PATCH/DELETE /api/app/v1/assistant/rules...` | 仅 C 阶段，持久化规则、权限和启停状态 |

提案至少含目标/时间范围/用户时区、候选任务、前提假设、待补充项、来源数据版本、有效期、变更清单、冲突和容量。owner 由可信会话或本机环境绑定，不能信任模型填入的用户 ID。

执行请求绑定提案版本、授权范围和幂等键；执行记录存实际变更项、来源身份、前后版本、结果和撤销条件。助手提案/偏好/运行历史有独立数据模型，不把原始聊天写进业务表或审计日志。历史保留期限、清除入口与云端删除行为需在契约评审时确定。

## 12. 可靠性与异常行为

| 情况 | 期望行为 |
|---|---|
| 缺少目标、期限或可用时段 | 指出缺失项；草稿可标注假设，实际写入需完整条件 |
| 用户要求 45 分钟、跨午夜或跨自然年区间 | 说明现有限制，提供明确可选拆分；不静默舍入或改变日期语义 |
| 可用时间不足或与锁定任务冲突 | 展示缺口与替代方案，不强塞入日程 |
| 模型超时、额度耗尽、格式非法、未知动作 | 保留用户输入；不写业务数据；明确失败，可切换离线规则 |
| 执行期间退出/切换账号或 ownerScope 不一致 | 拒绝旧提案执行，重新读取当前身份上下文 |
| 预览后另一设备改动相同任务 | 版本校验拒绝过期提案，返回新差异，不能静默覆盖 |
| 请求超时但保存可能已完成 | 查询执行记录后确认；不重新生成操作标识重复提交 |
| 重复点击、恢复后重放 | 同一操作幂等返回原结果 |
| 批量有部分成功 | 精确列成功/失败/冲突；只重试未完成项，不显示整批完成 |
| 用户撤销后续已被修改的任务 | 拒绝直接恢复旧快照，展示冲突；不能抹掉其他设备修改 |
| 规则暂停、权限收回、已过触发有效期 | 执行前再次检查，停止待执行写入；不晚到后批量补做 |
| 手机后台延迟、电脑关机 | 显示未执行或延迟的事实，避免承诺准点成功 |

撤销是带版本检查的新业务变更，不是删除执行历史，也不是简单恢复整个数据库。业务操作审计只保存必要 ID、数量、结果与耗时；不得记录 token、邮件地址、凭据或完整请求正文。

## 14. 费用与运行策略

- 按用户主动请求和有意义的事件调用模型，不逐字输入调用、不固定高频轮询。
- 只发送相关日期和必要任务摘要；使用真实数据版本判断是否可以复用提案。
- 设置每用户调用额度、并发限制、输出上限与规则运行次数；达到上限时保留手动计划和离线规则。
- 高阶模型仅用于复杂目标拆解；是否采用多档模型在样本表现与成本核验后决定。
- 成本估算按“活跃用户 × 主动调用次数 + 规则触发次数”，结合输入/输出长度、供应商价格、服务端运行与存储成本计算；本轮不给无依据的金额或工期。
